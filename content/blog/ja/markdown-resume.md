## なぜ職務経歴書を Markdown で書くのか？

職務経歴書（レジュメ）は、人生でもっとも重要な文書のひとつです。それなのに多くの人は、最悪の方法で作っています。Microsoft Word のテンプレートと格闘し、余白をピクセル単位で調整し、PDF で保存したときにレイアウトが崩れないよう祈るのです。

Markdown で職務経歴書を書くのは、根本的に異なるアプローチです。内容、構成、情報に集中し、書式は CSS や変換ツールで別に扱います。内容と見た目を分けることには、実用的なメリットがいくつもあります。

**バージョン管理**：職務経歴書を Git で管理し、すべての変更を追跡できます。業界や職種ごとに異なるバージョンをブランチで作り、いつ何を変えたのかを正確に確認できます。

**ひとつのソースから複数の形式**：ひとつの Markdown ファイルから PDF、HTML、Word 版を作れます。内容を書き直さずに、場面に応じて CSS テーマを切り替えられます。

**更新が簡単**：新しい職歴やスキルの追加は数秒で済みます。テキストボックスや表と格闘したり、1 行挿入しただけで書式が崩れたりすることはありません。

**プレーンテキストの耐久性**：何十年経っても、どんなテキストエディタでも職務経歴書を読めます。独自形式に縛られることも、互換性の問題もありません。

**ATS との相性**：正しく PDF に変換すれば、Markdown の職務経歴書は応募者追跡システム（ATS）が簡単に読み取れる、すっきりと解析しやすいテキストになります。

## 伝わる内容を書く

### 職務要約

職務要約は 3〜4 行で、「なぜこの人を採用すべきなのか？」という問いに答えましょう。経験のレベル、中心となる専門性、ほかの人との違いから書き始めます。

```markdown
## 職務要約

スケーラブルな Web アプリケーション開発で
8 年の経験を持つシニアソフトウェアエンジニア。
React、Node.js、クラウドアーキテクチャを専門とする。
5〜12 名のエンジニアチームを率いた経験あり。
開発者体験とコード品質の向上に情熱を持つ。
```

「チームプレーヤー」「勤勉」のような、ありきたりな言葉は避けましょう。具体的なスキルと、測定可能な経験を書きます。

### 職務経歴の項目

各職歴の箇条書きは、**行動を表す動詞 + 何をしたか + 測定可能な成果** という型に沿って書きましょう。

```markdown
- モノリシックなアプリケーションのマイクロサービス化を主導し、
  デプロイ時間を 45 分から
  5 分に短縮
```

次のようには書きません。

```markdown
- マイクロサービス移行プロジェクトに携わった
```

1 つ目の書き方なら、何をして、どんな影響があったのかが読み手に正確に伝わります。2 つ目の書き方では、ほとんど何も伝わりません。

### 力強い動詞

具体的でインパクトのある言葉を使いましょう。

| 弱い表現       | 強い表現                       |
|:---------------|:-------------------------------|
| 携わった       | 設計した、構築した、実装した   |
| 手伝った       | 主導した、指導した、調整した   |
| 担当した       | 管理した、統括した、納品した   |
| 行った         | 設計した、最適化した、自動化した |

### すべてを数字で示す

数字があると、職務経歴書は具体的で信頼できるものになります。

- 「API のレスポンス時間を **60%** 短縮」
- 「**1 日 200 万人以上のアクティブユーザー**が利用」
- 「コードカバレッジを **45% から 85%** に向上」
- 「**5〜12 名のエンジニア**チームを統括」
- 「**毎秒 1 万件以上のリクエスト**を処理」

正確な数字がなければ、妥当な見積もりを使いましょう。「ページの読み込み時間を大幅に改善」よりも「ページの読み込み時間を約 40% 改善」のほうが説得力があります。

## CSS でスタイルを整える

Markdown の職務経歴書は、CSS を適用したときに本領を発揮します。同じ内容でも、スタイルシートを変えるだけでまったく違う見た目になります。

## PDF に変換する

### printmd を使う

printmd は、すっきりとした組版と適切なページレイアウトを重視しているので、職務経歴書の変換に向いています。Markdown の職務経歴書を読み込み、CSS テーマを適用して PDF に書き出すだけです。デザインツールで作ったものに負けない、プロ品質の文書に仕上がります。

職務経歴書での主なメリットは次のとおりです。

- どのプラットフォームでも同じように表示される
- 2 ページにわたる場合も改ページを適切に処理する
- 文字サイズ、行間、余白などの組版を調整できる
- ローカルで処理するので個人情報が外部に出ない

### Pandoc を使う

コマンドラインに慣れている人なら、Pandoc と LaTeX テンプレートや CSS を組み合わせて、プロ品質の結果を得られます。

```bash
# 既定の LaTeX スタイルで変換
pandoc resume.md -o resume.pdf

# HTML を経由してカスタム CSS を適用
pandoc resume.md -o resume.pdf \
  --css=resume-theme.css \
  --pdf-engine=wkhtmltopdf

# カスタム LaTeX テンプレートを使う
pandoc resume.md -o resume.pdf \
  --template=resume-template.tex
```

### md-to-pdf を使う

```bash
md-to-pdf resume.md --stylesheet resume-theme.css
```

## ATS に強い出力

応募者追跡システム（ATS）は、人間が目を通す前に職務経歴書をスキャンします。美しくデザインされた職務経歴書の多くが ATS の解析で落ちてしまうのは、画像や複雑なレイアウト、標準的でない書式を使っているからです。

Markdown の職務経歴書は、ソースが構造化されたプレーンテキストなので、この点で生まれつき有利です。正しく PDF に変換すれば、テキストのレイヤーはすっきりとして解析しやすいものになります。

### ATS に対応するためのコツ

**標準的なセクション見出しを使う。** ATS は認識できる見出しを探します。

```markdown
## 職務経歴       （「これまで働いた場所」ではなく）
## 学歴           （「学びの歩み」ではなく）
## スキル         （「私の道具箱」ではなく）
```

**レイアウトに表を使わない。** 表は表形式のデータにだけ使いましょう。ATS は表を使ったレイアウトを読み違えることがあります。

**求人票のキーワードを入れる。** 求人に「React」「TypeScript」「マイクロサービス」とあれば、まったく同じ言葉が職務経歴書に含まれるようにしましょう。

**標準的な日付の書式を使う。** 「2022 年 1 月〜現在」や「2022/01〜現在」ならどちらでもかまいません。「22/1〜今」のような書き方は避けましょう。

**画像やアイコンを使わない。** ATS は画像を読めません。連絡先を画像にしてしまうと、システムからはまったく見えなくなります。

**1 段組みのレイアウトにする。** 多段組みのレイアウトは多くの ATS を混乱させます。シンプルにしましょう。

## 複数のバージョンを管理する

Markdown の職務経歴書の大きな利点のひとつは、複数のバージョンを効率よく管理できることです。

```
resume/
  base-resume.md          # すべての経歴を含む完全版
  resume-frontend.md      # フロントエンド職向け
  resume-fullstack.md     # フルスタック職向け
  resume-leadership.md    # マネジメント経験を強調
  themes/
    professional.css
    minimal.css
    modern.css
```

基本の職務経歴書にはすべてを書いておきます。職種ごとのバージョンでは、関係のないセクションを削り、その職種にもっとも関連する経験を強調します。

Git を使えば、すべてのバージョンの変更を追跡し、各バージョンが基本版とどう違うのかを正確に確認できます。

## 避けるべきよくある間違い

### 長すぎる

ほとんどの人にとって、1 ページが理想です。経験豊富なシニア職なら 2 ページでもかまいません。3 ページが適切なことはまずありません。

### ありきたりな内容

「Web アプリケーションの開発を担当」では、具体的なことが何も伝わりません。箇条書きの一つひとつが、あなた自身の経験に固有のものであるべきです。

### 書式がばらばら

箇条書きの末尾に句点があったりなかったり、時制や語調が入り混じっていたりすると、細部への注意が足りない印象を与えます。Markdown は構造がはっきりしているので、一貫性を保ちやすくなります。

### 連絡先の書き漏れ

職務経歴書には必ず、氏名、メールアドレス、電話番号、所在地（市区町村まで）を書きましょう。技術職なら LinkedIn と GitHub のプロフィールもぜひ載せましょう。

### 嘘や誇張

誇張した内容は、面接やリファレンスチェックで見抜かれます。それよりも、実際の実績を説得力のある形で示しましょう。

## まとめ

Markdown の職務経歴書なら、いいとこ取りができます。自分で完全にコントロールできる、すっきりと構造化された内容と、必要なときに作れるプロ品質の PDF です。内容は一度書けばよく、Git で管理し、応募先に合わせたバージョンを作れます。

流れはシンプルです。Markdown で書き、CSS でスタイルを整え、printmd や Pandoc で PDF に変換して、自信を持って応募しましょう。面接につながるのは職務経歴書の中身です。Markdown は、その中身をすっきりと最新の状態に保ち、美しく見せることを簡単にしてくれます。
