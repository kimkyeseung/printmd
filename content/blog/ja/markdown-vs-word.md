## 形式をめぐる大論争

ライター、開発者、ナレッジワーカーなら誰もが、いつかこの問いに直面します。Markdown で書くべきか、それとも Microsoft Word（や Google ドキュメント）のようなワープロソフトで書くべきか。テクノロジーの多くの問題と同じく、答えは「場合による」です。どちらの形式も、異なる人の異なる問題を解決するために存在しています。

この記事では、場面ごとに適したツールを選べるよう、率直に比較します。結論を先に言ってしまうと、状況に応じて両方を使い分けるのが最善であることが多いです。

## ひと目でわかる比較

| 項目                     | Markdown                         | Microsoft Word                   |
|:-------------------------|:---------------------------------|:---------------------------------|
| ファイル形式             | プレーンテキスト（.md）          | バイナリ/XML（.docx）            |
| ファイルサイズ           | ごく小さい（KB 単位）            | 大きめ（MB 単位になることも）    |
| 専用ソフトの必要性       | 不要（どのテキストエディタでも） | 必要（Word、Google ドキュメントなど） |
| 習得のしやすさ           | 少しの構文を覚えるだけ           | WYSIWYG で多くの人には直感的     |
| バージョン管理（Git）    | 非常に優れている                 | 苦手（バイナリの差分）           |
| リアルタイム共同編集     | 限定的（別のツールが必要）       | 非常に優れている（標準搭載）     |
| 見た目の書式             | ソース上では最小限               | 完全な WYSIWYG                   |
| テンプレートとスタイル   | CSS や変換ツールで実現           | テンプレートとテーマを標準搭載   |
| 目次                     | 手動またはツールで生成           | 自動                             |
| 変更履歴                 | Git や差分ツールで管理           | 標準搭載                         |
| 書き出し形式             | HTML、PDF、DOCX、EPUB など       | PDF、HTML、プレーンテキストなど  |
| 数式                     | LaTeX 記法                       | 数式エディタを標準搭載           |
| オフラインでの利用       | 常に可能（プレーンテキスト）     | 常に可能（デスクトップアプリ）   |
| 費用                     | 無料                             | サブスクリプション（年 $70〜100） |

## Markdown が勝る場面

### 開発者向けドキュメント

コードと一緒に管理するドキュメントを書くなら、Markdown が文句なしの勝者です。Git とシームレスに連携し、GitHub や GitLab でそのまま表示され、MkDocs、Docusaurus、VitePress などの静的サイトジェネレーターでも処理できます。

````markdown
## API エンドポイント

### GET /api/users

すべてのユーザーの一覧を返します。

```bash
curl https://api.example.com/users \
  -H "Authorization: Bearer TOKEN"
```
````

これを Word 文書に入れて、Git で変更を追跡してみてください。うまくいきません。

### コードを含む技術文書

コードスニペットを含む文書なら、どれも Markdown の恩恵を受けられます。言語ごとのハイライトが付くフェンスドコードブロックは、Markdown のもっとも強力な機能のひとつです。

````markdown
```python
def calculate_total(items):
    return sum(item.price * item.quantity for item in items)
```
````

Word では、コードの書式設定には手作業でのフォント変更が必要で、シンタックスハイライトは外部ツールやスクリーンショットに頼るしかありません。

### Git によるバージョン管理と共同作業

Markdown ファイルはプレーンテキストなので、Git はすべての変更を行単位で追跡できます。各コミットで何が追加、削除、変更されたのかを正確に確認できます。ドキュメントのレビューも、ソフトウェアのコードレビューと同じくらい自然に行えます。

Word 文書はバイナリファイルです。Git に保存することはできますが、差分の確認やマージは事実上不可能です。Word で共同執筆するには、リアルタイムの共同編集（Word はこれをうまくサポートしています）を使うか、メールでファイルをやり取りする面倒な方法をとるしかありません。

### スピードと移植性

Markdown ファイルは、どの OS のどのテキストエディタでも一瞬で開けます。読み込み時間も、互換性のチェックも、「このファイルは新しいバージョンで作成されました」という警告もありません。2004 年に作成された Markdown ファイルは今でも完璧に開いて表示でき、何十年先もそのまま使えます。

### 手軽な公開

ブログ、静的 Web サイト、ナレッジベースでは、Markdown が標準の入力形式です。ほとんどの静的サイトジェネレーター、CMS、Wiki ツールが Markdown にそのまま対応しています。

### 集中して書ける

Markdown なら、書いている途中でフォント、行間、レイアウトをいじりたくなる誘惑がなくなります。何十もの書式オプションが並んだツールバーが注意を引くこともありません。まず内容を書き、見た目はあとで整えます。この関心の分離が、よりよい文章につながることがよくあります。

## Word が勝る場面

### 技術者ではない読者向けのビジネス文書

読み手が Word 文書を期待しているなら、Word 文書を渡しましょう。企業のクライアントや法務部門に `.md` ファイルを送れば、混乱を招くだけです。Word はビジネスコミュニケーションの共通語です。

### 複雑な見た目の書式

正式な手紙、法的文書、書式の凝ったレポートなど、正確な見た目のレイアウトが求められる文書は Word のほうが作りやすいです。WYSIWYG の編集なら、印刷したページがどう見えるかを書きながら正確に確認できます。

### リアルタイムの共同編集

Microsoft 365 と Google ドキュメントは、リアルタイムの共同編集に優れています。複数の作成者が同時に編集し、コメントを残し、変更を提案し、修正履歴を追跡できます。すべて同じ画面の中で完結します。HackMD や HedgeDoc のように Markdown の共同編集ができるツールもありますが、完成度やなじみやすさでは Word や Google ドキュメントにかないません。

### 技術者ではないユーザー

誰もが Markdown の構文を覚えたいと思うわけではありません。デザイナー、マーケター、経営陣、クライアントなど、技術者ではないメンバーを含むチームにとって、Word はトレーニング不要のなじみのある環境です。

### 正確な印刷レイアウト

Word では、ページレイアウト、ヘッダー、フッター、余白、印刷設定を細かく制御できます。Markdown から PDF への変換ツールは大きく進歩しましたが、印刷レイアウトをピクセル単位で詰める必要がある文書では、今でも Word のほうが正確です。

### テンプレートとブランディング

企業では、特定のフォント、色、ヘッダー、フッターの内容など、ブランドのガイドラインに沿った文書が求められることがよくあります。Word のテンプレートならこれを簡単に実現できます。Markdown で同じ結果を得るには、カスタム CSS と、それに対応した変換ツールが必要です。

## 両方を使い分ける

もっとも生産的なのは、それぞれのツールを得意な場面で使うことです。

- **Markdown**：ドキュメント、README、ブログ記事、技術メモなど、Git リポジトリで管理するすべてのもの。
- **Word/Google ドキュメント**：ビジネスの提案書、クライアント向けのレポート、共同で作る下書き、複雑な見た目の書式が必要な文書。

多くのワークフローでは、Markdown で書いてから、配布用にほかの形式へ変換します。

### Markdown を Word に変換する

Pandoc を使えば簡単に変換できます。

```bash
pandoc document.md -o document.docx

# カスタムの Word テンプレートを使う
pandoc document.md -o document.docx --reference-doc=template.docx
```

`--reference-doc` オプションを使うと、会社の Word テンプレート（フォント、色、ヘッダー）が変換後の文書に適用されます。Markdown で書いて、Word で納品できます。

### Word を Markdown に変換する

逆方向の変換もできます。

```bash
pandoc document.docx -o document.md

# 画像も取り出す
pandoc document.docx -o document.md --extract-media=./images
```

既存の Word のドキュメントを Markdown ベースの仕組みに移行したいときに便利です。

### Markdown を PDF に変換する

Word も生の Markdown も納品形式としてふさわしくない場合、PDF が万能の答えになります。printmd のようなツールを使えば、適切な組版、改ページ、レイアウトで、Markdown をプロ品質の PDF に変換できます。Markdown で書くシンプルさと、整った文書のプロらしい見た目の両方が手に入ります。

## 実際のシナリオ

### シナリオ 1：ソフトウェアプロジェクトのドキュメント

**最適な選択：Markdown。**
ドキュメントはコードと同じリポジトリに置くべきです。開発者はコードの変更と同じプルリクエストでドキュメントを更新できます。ドキュメントは静的 Web サイトとして自動でデプロイできます。

### シナリオ 2：四半期ごとの業績レポート

**最適な選択：Word または Google ドキュメント。**
複数の関係者がレビューしてコメントする必要があります。グラフ、ブランディング、正確なレイアウトが求められます。読み手は `.docx` か PDF を期待しています。

### シナリオ 3：個人のブログ

**最適な選択：Markdown。**
ほとんどの静的サイトジェネレーターと CMS は Markdown を使います。速く、移植性があり、将来も使い続けられます。

### シナリオ 4：学術論文

**最適な選択：場合による。**
数式や引用が多い論文なら、LaTeX（または LaTeX 拡張付きの Markdown）が理想的です。共同執筆者が技術者でなければ、Google ドキュメントのほうが現実的かもしれません。多くの研究者は Markdown と Pandoc で執筆し、求められる投稿形式に変換しています。

### シナリオ 5：議事録

**最適な選択：Markdown。**
すばやく書けて、共有しやすく、バージョン管理もできます。Markdown のテンプレートを使えば、チーム全体で議事録の形式をそろえられます。

### シナリオ 6：クライアントへの提案書

**最適な選択：Word または Google ドキュメント。**
クライアントがコメントしたり変更を提案したりする必要があります。ブランドのテンプレートを適用しなければなりません。最終版には署名が必要になることもあります。

## 移行の進め方

今は何でも Word で書いていて、ワークフローに Markdown を取り入れたいなら、小さなことから始めましょう。

1. **個人のメモ**：メモを Markdown で取るようにしましょう。Obsidian や VS Code などのツールを使えば、無理なく移行できます。
2. **議事録**：Markdown のテンプレートで議事録を取りましょう。
3. **社内ドキュメント**：チームの Wiki や社内ドキュメントを Markdown に移しましょう。
4. **ブログ記事**：ブログを持っているなら、記事を Markdown で書きましょう。
5. **プロジェクトの README**：構成の整った README.md から始めましょう。

Word を完全に置き換えようとしないことです。それぞれのツールに役割を果たさせましょう。そのうち、どの場面でどの形式を選べばよいか、直感的にわかるようになります。

## まとめ

Markdown と Word は競合するものではありません。異なるニーズを満たす、補い合うツールです。Markdown はスピード、移植性、バージョン管理、技術的な内容に優れています。Word は見た目の書式、共同作業、ビジネスコミュニケーションに優れています。

問うべきは「どちらが優れているか」ではなく、「この作業にはどちらが適しているか」です。ひとつのツールですべてをこなそうとするのをやめれば、執筆のワークフローは格段に効率的になります。

Markdown の長所のために Markdown を学び、Word の長所のために Word を使い続け、必要に応じて変換しましょう。それが現実的な道です。
