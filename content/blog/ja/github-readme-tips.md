## README が重要な理由

README はプロジェクトの玄関です。GitHub のリポジトリを訪れた人が最初に目にするのが README です。多くの場合、そのプロジェクトを使うか、貢献するか、立ち去るかを決める前に読む唯一のものでもあります。

よく書かれた README は、ふらりと訪れた人をアクティブなユーザーやコントリビューターに変えます。逆に出来の悪い README、さらに悪いことに README がない場合は、プロジェクトが放置されている、メンテナンスされていない、あるいは理解しようとする価値がない、というサインになってしまいます。

オープンソースの採用傾向に関する調査では、開発者がライブラリを選ぶ際の最も大きな要因のひとつがドキュメントの質であることが繰り返し示されています。コードがどれほど優れていても、最初の 30 秒で何をするものか、どう使うのかが伝わらなければ、人は別のものを探しに行きます。

## 基本の構成

優れた README は長い必要はありません。必要なのは構成です。小さなユーティリティから大規模なフレームワークまで、ほとんどのプロジェクトで使えるテンプレートを紹介します。

### プロジェクト名と説明

まず明確で簡潔なタイトルと、プロジェクトが何をするのかを説明する 1 段落の文章から始めます。

```markdown
# printmd

美しいレイアウトの文書を作れる Markdown → PDF 変換ツール。
Markdown で書いて、プロ品質の組版とレイアウトで
PDF に書き出せます。
```

説明では専門用語を避けましょう。プロジェクトのことを一度も聞いたことがない人に向けて書きます。「これは何をするもので、なぜ自分に関係があるのか？」という問いに答えましょう。

### バッジ

バッジを使うと、プロジェクトの状態がひと目でわかります。説明のすぐ下に配置しましょう。

```markdown
![Build Status](https://img.shields.io/github/actions/workflow/status/user/repo/ci.yml)
![npm version](https://img.shields.io/npm/v/package-name)
![License](https://img.shields.io/github/license/user/repo)
![Downloads](https://img.shields.io/npm/dm/package-name)
```

よく使われるバッジは次のとおりです。

- **ビルドステータス**：CI/CD が通っているかどうか。
- **バージョン**：現在のリリースバージョン。
- **ライセンス**：MIT、Apache、GPL など。
- **ダウンロード数**：月間または累計のダウンロード数。
- **カバレッジ**：テストカバレッジの割合。

バッジは付けすぎないようにしましょう。5〜7 個が妥当な上限です。多すぎると見た目が散らかるだけで、価値は増えません。

### スクリーンショットやデモ

百聞は一見にしかず。見た目のあるプロジェクトなら、実際に見せましょう。

```markdown
## デモ

![printmd で Markdown ファイルを PDF に変換している様子](./screenshots/demo.gif)

[ライブデモ](https://printmd.app/demo)で実際の動作を試せます。
```

コマンドラインツールの場合は、asciinema などのターミナル録画ツールを使ったり、動作の様子を GIF にしたりするとよいでしょう。

### インストール

対応しているすべての方法について、コピー＆ペーストでそのまま使える明確な手順を書きます。

````markdown
## インストール

### npm

```bash
npm install printmd
```

### yarn

```bash
yarn add printmd
```

### Homebrew

```bash
brew install printmd
```
````

動作要件があれば書いておきましょう。ユーザーに推測させてはいけません。Node.js 18 以上、Python 3.9 以上、特定の OS などが必要なら、はっきり明記します。

### クイックスタート／使い方

できるだけシンプルな使用例を示します。インストールから動く結果までを、なるべく少ない手順で体験してもらいましょう。

````markdown
## クイックスタート

```bash
# Markdown ファイルを PDF に変換
printmd convert document.md

# オプションを指定して変換
printmd convert document.md --output report.pdf --theme professional
```
````

クイックスタートのあとに、より詳しい使用例を載せられます。

````markdown
## 使い方

### 基本的な変換

```javascript
import { convert } from 'printmd';

const pdf = await convert('# Hello World\n\nThis is my document.');
fs.writeFileSync('output.pdf', pdf);
```

### 設定オプション

| オプション | 型     | 既定値  | 説明                       |
|------------|--------|---------|----------------------------|
| theme      | string | default | PDF テーマ名               |
| fontSize   | number | 12      | 基本の文字サイズ（pt）     |
| margin     | string | 1in     | ページの余白               |
| pageSize   | string | A4      | 用紙サイズ（A4、Letter）   |
````

### API リファレンス

ライブラリなら、完全な API リファレンスを用意するか、そのリンクを載せましょう。README では少なくとも主要な関数をカバーします。

```markdown
## API

### `convert(markdown, options?)`

Markdown 文字列を PDF のバッファに変換します。

**引数：**
- `markdown`（string）：変換する Markdown の内容。
- `options`（object、省略可）：設定オプション。

**戻り値：** `Promise<Buffer>` - 生成された PDF のバッファ。
```

API が大きい場合は、すべてを README に書こうとせず、別のドキュメントサイトへのリンクにしましょう。

### コントリビューション

誰でも気軽に貢献できるようにします。

```markdown
## コントリビューション

コントリビューションを歓迎します！プルリクエストを送る前に
[コントリビューションガイド](CONTRIBUTING.md)を
お読みください。

1. リポジトリをフォークする
2. 機能ブランチを作成する（`git checkout -b feature/amazing-feature`）
3. 変更をコミットする（`git commit -m 'Add amazing feature'`）
4. ブランチにプッシュする（`git push origin feature/amazing-feature`）
5. プルリクエストを作成する
```

### ライセンス

ライセンスは必ず明記しましょう。

```markdown
## ライセンス

このプロジェクトは MIT ライセンスのもとで公開されています。
詳しくは [LICENSE](LICENSE) ファイルをご覧ください。
```

## README をよくするための書き方のコツ

### 能動態で、直接的に書く

「パッケージはインストールされる必要があります」ではなく「パッケージをインストールします」と書きましょう。直接的な指示のほうが従いやすくなります。

### 段落は短く

長い文章のかたまりは流し読みしにくいものです。1 段落は 3〜4 文までにし、機能や要件の一覧は箇条書きにしましょう。

### 「じっくり読む人」ではなく「流し読みする人」向けに書く

ほとんどの人は README を上から順に読むのではなく、ざっと目を通します。わかりやすい見出しを付け、重要な用語は太字に、コマンドはコードブロックに入れましょう。30 秒流し読みするだけで、何をするプロジェクトか、どうインストールするかがわかるのが理想です。

### エラーへの対処も書く

よくある問題を予想して、対処法を書いておきます。

```markdown
### トラブルシューティング

**エラー：`ENOENT: no such file or directory`**

入力ファイルのパスが正しく、ファイルが存在するか確認してください。

**エラー：`Cannot find module 'puppeteer'`**

`npm install` を実行して、すべての依存関係をインストールしてください。
```

### 常に最新に保つ

インストール手順が古かったり、非推奨の API の例が載っていたりする README は、ないよりも害になります。API を変更したら、同じプルリクエストで README も更新しましょう。

## README の応用テクニック

### 目次

長めの README には目次を付けましょう。

```markdown
## 目次

- [インストール](#インストール)
- [クイックスタート](#クイックスタート)
- [API リファレンス](#api-リファレンス)
- [設定](#設定)
- [コントリビューション](#コントリビューション)
- [ライセンス](#ライセンス)
```

GitHub は見出しのアンカーリンクを自動で生成するので、追加の設定なしでこれらのリンクが機能します。

### 折りたたみセクション

重要だけれどすべての読者に必要なわけではない内容には、HTML の details タグを使いましょう。

````markdown
<details>
<summary>高度な設定</summary>

プロジェクトのルートに `.printmdrc` ファイルを作成すると、
動作をカスタマイズできます。

```json
{
  "theme": "professional",
  "fontSize": 11,
  "pageSize": "Letter"
}
```

</details>
````

### 多言語対応

海外のユーザーもいるプロジェクトなら、README の翻訳版を用意することを検討しましょう。

```markdown
README: [English](README.md) | [한국어](README.ko.md) | [日本語](README.ja.md)
```

### 主な機能を目立たせる

冒頭近くに機能一覧を置くと、ユーザーはプロジェクトで何ができるのかをすぐに把握できます。

```markdown
## 特長

- **高速変換** - Markdown を数ミリ秒で PDF に変換
- **美しい組版** - プロ品質のフォントとレイアウトをすぐに使える
- **コードハイライト** - 100 以上の言語のシンタックスハイライト
- **ローカル処理** - ファイルがパソコンの外に出ることはありません
- **クロスプラットフォーム** - macOS、Windows、Linux で動作
```

## 優れた README の例

次のプロジェクトを参考にしてみてください。

- **freeCodeCamp/freeCodeCamp**：網羅的で、コントリビューションのガイドラインが明確。
- **vuejs/vue**：すっきり整理されていて、クイックスタートがしっかりしている。
- **sindresorhus/awesome**：シンプルでありながら効果的な README の好例。
- **nvm-sh/nvm**：CLI ツールのインストールと使い方を丁寧に説明している。

これらの README には共通点があります。構成が整っていて流し読みしやすく、制約について正直で、定期的に更新されていることです。

## README から PDF を作る

README を単独の文書として共有する必要がある場合、たとえばプロジェクト提案書やポートフォリオの一部として使う場合は、PDF に変換できます。printmd のようなツールなら、表、コードブロック、タスクリスト、バッジを含む GitHub 形式の Markdown もきれいに処理できます。

授業でのプロジェクト資料の提出、クライアントへのプレゼンテーション、助成金の申請など、PDF 形式が求められる場面で特に役立ちます。

## まとめ

優れた README は長さではなく、明快さ、構成、そして読み手の時間への配慮で決まります。基本（何を、なぜ、どうやって）を押さえ、実際に動く例を載せ、常に最新に保ちましょう。README はプロジェクトの顔です。しっかり作り込みましょう。

まずはこのガイドのテンプレートから始め、自分のプロジェクトに合わせて調整し、ユーザーから寄せられる質問をもとに磨き上げていきましょう。最高の README は、プロジェクトとともに進化し続ける「生きたドキュメント」です。
