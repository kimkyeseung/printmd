## 为什么用 Markdown 写会议纪要？

会议纪要有一项关键作用：为决策、待办事项和讨论内容留下共同的记录。没有好的纪要，会议就会变成一个黑洞，信息进去了就再也出不来。大家离开会议室时对达成的共识理解各不相同，待办事项被遗忘，同样的话题到下次会议又要再讨论一遍。

Markdown 非常适合写会议纪要，因为它解决了几个常见问题：

**速度**：开会时可以快速记录信息。Markdown 的语法极简，按下的每个键都用在内容上，而不是排版上。一个短横线就是项目符号，一对方括号就是复选框，完全不用点鼠标。

**结构**：Markdown 的标题和列表会自然地为纪要带来结构。不再是一大段密密麻麻的文字，而是会后便于浏览的条理分明的章节。

**可搜索**：纯文本文件很容易搜索。半年后，当你需要找到做出某个决定的那次会议时，在纪要文件夹里简单搜一下就能找到。

**可移植**：Markdown 文件在哪里都能用。不需要特定软件，体积很小，几十年后依然能读。不会因为订阅到期而打不开自己的会议记录。

**版本控制**：如果团队使用 Git，会议纪要可以和项目放在同一个仓库里。修改会被跟踪，完整的历史也会保留下来。

## 会议纪要模板

好的模板能让每次会议的记录保持一致，也更容易记下该记的信息。下面这个模板适用于大多数团队：

```markdown
---
title: "每周站会 - 产品团队"
date: 2025-03-15
attendees:
  - Alice Chen
  - Bob Martinez
  - Carol Kim
  - David Park
absent:
  - Eve Johnson（休假）
---
```

## 模板逐项解析

### 头部信息

头部记录最基本的元数据：谁参加了、什么时间、在哪里。使用 YAML front matter 可以让这些信息便于机器读取，日后如果想做解析会议纪要的工具，这会很有用。

```markdown
---
title: "每周站会 - 产品团队"
date: 2025-03-15
attendees:
  - Alice Chen
  - Bob Martinez
---
```

### 议程

在会前写好议程。这能让大家对会议有预期，也能让讨论保持聚焦。开会时，你可以在每个议程项下面记笔记，而不是按时间顺序把所有内容写成一长串。

### 讨论记录

记要点，而不是每一句话。会议纪要不是逐字稿。重点记录：

- 影响决策的发言
- 提出的顾虑或反对意见
- 分享的数据或事实
- 日后会用到的背景信息

把发言对应到具体的人。这样责任更清晰，后续跟进也更方便。

### 决定

把决定和讨论分开。单独列出“决定”一节，能让人一眼看出哪些是真正定下来的，哪些只是讨论过。给决定编号，方便在后续沟通中引用。

### 待办事项

这是最重要的部分。每个待办事项都应包含：

- **做什么**：清晰描述任务
- **谁来做**：负责人（一个人，而不是一个小组）
- **何时完成**：明确的截止日期

用 Markdown 复选框（`- [ ]`）可以方便地跟踪完成情况：

```markdown
- [x] **Alice**：搭建预发布环境 - **截止：3 月 10 日**（已完成）
- [ ] **Bob**：编写 API 文档 - **截止：3 月 18 日**
```

## 整理会议纪要

### 文件夹结构

```
meetings/
  team-standup/
    2025-03-01.md
    2025-03-08.md
    2025-03-15.md
  one-on-ones/
    alice/
      2025-03-05.md
      2025-03-19.md
    bob/
      2025-03-07.md
      2025-03-21.md
  client/
    acme-corp/
      2025-03-15.md
    beta-inc/
      2025-03-12.md
  retrospectives/
    sprint-14.md
    sprint-15.md
```

### 命名规范

用日期作为文件名的前缀：`2025-03-15.md` 或 `2025-03-15-weekly-standup.md`。这样文件默认就会按时间排序，按日期查找也易如反掌。

### 链接相关纪要

话题跨会议延续时，在纪要之间交叉引用：

```markdown
## 延续自 [3 月 8 日站会](./2025-03-08.md)

David 的货币 bug 仍未解决。参见
[最初的讨论](./2025-03-08.md#blockers)。
```

## 分享与归档

### 会后分享

在会议结束后一小时内发出纪要。拖得越久，纪要的价值就越低。常见的分享方式有：

1. **Git 提交**：把纪要推送到共享仓库，团队成员会通过日常的 Git 工作流程收到通知。
2. **邮件**：对于不使用 Git 的相关方，发送一封总结邮件，并附上 PDF 版纪要。printmd 这样的工具可以把 Markdown 纪要转换成整洁的 PDF。
3. **Slack/Teams**：在团队频道里发一段总结，并附上完整纪要的链接。
4. **Confluence/Notion**：有些团队更喜欢用 Wiki 管理文档。你可以先用 Markdown 写，再粘贴到这些工具中。

### 归档策略

会议纪要的“保质期”各不相同。半年前的站会记录很少会用到，但客户会议纪要或决策记录可能在几年后还会被翻出来。

可以考虑这样的归档方式：

- **活跃纪要**：本季度的纪要，放在主文件夹里方便查阅。
- **归档**：较早的纪要移到 `archive/` 文件夹，按年份整理。
- **永久记录**：决策日志和客户会议纪要永久保存。

## 写好会议纪要的技巧

### 会前

- 准备好模板，并填好议程。
- 回顾上次会议的待办事项。
- 把议程发给参会人，让大家提前准备。

### 会中

- 重点记录决定和待办事项，而不是每一句发言。
- 可以用缩写和简写，会后再整理。
- 记下谁说了什么，明确责任。
- 用醒目的标记标出需要跟进的事项。

### 会后

- 趁讨论内容还新鲜，在一小时内整理好纪要。
- 和负责人确认待办事项。
- 及时分享纪要。
- 补上会上提到的链接、文档或参考资料。

### 不要逐字记录

会议纪要不是会议逐字稿。记录的是实质内容，而不是对话本身。如果有人花了五分钟讨论一个话题，纪要里可能只需要两句话概括要点，再加一条待办事项。

## 与 Markdown 会议纪要相得益彰的工具

- **Obsidian**：非常适合把会议纪要和项目笔记链接起来，构建讨论内容的知识图谱。
- **VS Code**：带 Markdown 预览和 Git 集成，编辑迅速。
- **printmd**：需要与偏好正式文档的相关方分享时，把纪要转换成 PDF。
- **Git**：为纪要做版本控制，跟踪修改、保留历史。
- **grep/ripgrep**：在命令行中瞬间搜索所有会议纪要。

## 总结

用 Markdown 写会议纪要，写得快、搜得到、分享也简单。关键在于保持一致：使用同一个模板，遵循同样的命名规范，每次会后都及时分享纪要。

从本指南的模板开始，根据团队需要加以调整，让写会议纪要成为一种习惯，而不是事后才想起来的事。在好纪要上投入的三十分钟，能为日后省下许多因困惑和重复讨论而浪费的时间。
