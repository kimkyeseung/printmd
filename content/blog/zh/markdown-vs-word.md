## 关于格式的大讨论

每个写作者、开发者和知识工作者迟早都会遇到这个问题：我该用 Markdown 写作，还是用 Microsoft Word（或 Google Docs）这类文字处理软件？和技术领域的大多数问题一样，答案是“看情况”。两种格式之所以都存在，是因为它们为不同的人解决不同的问题。

本文做一次客观的对比，帮你在不同场合选对工具。先剧透一下：最好的做法往往是根据场合两者并用。

## 快速对比

| 特性                 | Markdown                       | Microsoft Word                 |
|:---------------------|:-------------------------------|:-------------------------------|
| 文件格式             | 纯文本（.md）                  | 二进制/XML（.docx）            |
| 文件大小             | 极小（KB 级）                  | 较大（常达 MB 级）             |
| 是否需要专门软件     | 否（任何文本编辑器均可）       | 是（Word、Google Docs 等）     |
| 学习曲线             | 只需学少量语法                 | 所见即所得，大多数人上手即会   |
| 版本控制（Git）      | 极佳                           | 较差（二进制差异）             |
| 实时协作             | 有限（需要额外工具）           | 极佳（内置）                   |
| 视觉排版             | 源文件中很少                   | 完整的所见即所得               |
| 模板与样式           | 通过 CSS 或转换工具实现        | 内置模板和主题                 |
| 目录                 | 手动或由工具生成               | 自动生成                       |
| 修订跟踪             | 通过 Git 或比对工具            | 内置                           |
| 导出选项             | HTML、PDF、DOCX、EPUB 等       | PDF、HTML、纯文本等            |
| 数学公式             | LaTeX 语法                     | 内置公式编辑器                 |
| 离线使用             | 随时可用（纯文本）             | 随时可用（桌面应用）           |
| 费用                 | 免费                           | 订阅制（每年 $70-100）         |

## Markdown 更胜一筹的场景

### 开发者文档

如果你写的文档要和代码放在一起，Markdown 显然是赢家。它与 Git 无缝集成，在 GitHub 和 GitLab 上原生渲染，还能交给 MkDocs、Docusaurus、VitePress 等静态网站生成器处理。

````markdown
## API 端点

### GET /api/users

返回所有用户的列表。

```bash
curl https://api.example.com/users \
  -H "Authorization: Bearer TOKEN"
```
````

试试把这些内容放进 Word 文档，再用 Git 跟踪修改——效果可不怎么样。

### 含代码的技术写作

凡是包含代码片段的文档，都能从 Markdown 中受益。带语言高亮的围栏代码块语法，是 Markdown 最强大的功能之一：

````markdown
```python
def calculate_total(items):
    return sum(item.price * item.quantity for item in items)
```
````

在 Word 中，代码格式需要手动更换字体，语法高亮则只能借助外部工具或截图来实现。

### 借助 Git 进行版本控制与协作

Markdown 文件是纯文本，这意味着 Git 能按行跟踪每一处修改。你可以清楚地看到每次提交中添加、删除或修改了什么。文档的评审也能像代码评审一样自然。

Word 文档是二进制文件。Git 虽然能存储它们，但比对和合并几乎不可能实现。用 Word 协作写作，要么依靠实时共同编辑（Word 在这方面支持得很好），要么就得通过邮件来回发送文件，十分繁琐。

### 速度与可移植性

Markdown 文件在任何操作系统的任何文本编辑器中都能瞬间打开。没有加载时间，没有兼容性检查，也不会弹出“此文件由更新版本创建”的警告。2004 年创建的 Markdown 文件，今天依然能完美打开和渲染，几十年后也照样能用。

### 轻量级发布

对于博客、静态网站和知识库来说，Markdown 是标准的输入格式。大多数静态网站生成器、CMS 平台和 Wiki 工具都原生支持 Markdown。

### 无干扰写作

Markdown 消除了边写边摆弄字体、间距和版式的诱惑。没有一个摆满几十种格式选项的工具栏来分散你的注意力。先写内容，再处理呈现。这种关注点的分离，往往能让文章写得更好。

## Word 更胜一筹的场景

### 面向非技术读者的商务文档

如果读者期待收到 Word 文档，那就给他们 Word 文档。把 `.md` 文件发给企业客户或法务部门只会造成困惑。Word 是商务沟通的通用语言。

### 复杂的视觉排版

正式信函、法律文书或格式繁复的报告等需要精确视觉布局的文档，用 Word 制作更容易。所见即所得的编辑方式，让你在写作时就能准确看到打印出来的样子。

### 实时协作

Microsoft 365 和 Google Docs 在实时协作方面表现出色。多位作者可以同时编辑、留下批注、提出修改建议并跟踪修订，所有操作都在同一个界面中完成。虽然 HackMD 和 HedgeDoc 等工具也提供 Markdown 协同编辑，但在完善程度和熟悉度上都比不上 Word 或 Google Docs。

### 非技术用户

并不是每个人都愿意学 Markdown 语法。对于包含非技术成员的团队——设计师、市场人员、管理层或客户——Word 提供了无需培训就能上手的熟悉界面。

### 精确的打印版式

Word 能让你精细地控制页面布局、页眉、页脚、页边距和打印设置。尽管 Markdown 转 PDF 的工具已经有了长足进步，但对于打印版式要求精确到像素的文档，Word 仍然更精准。

### 模板与品牌规范

企业环境中，文档往往需要遵循品牌规范，使用特定的字体、颜色、页眉和页脚内容。用 Word 模板可以轻松做到。而要用 Markdown 达到同样的效果，就需要自定义 CSS 以及支持它的转换工具。

## 混合使用

最高效的做法，是让每个工具在它最擅长的地方发挥作用：

- **Markdown** 用于文档、README、博客文章、技术笔记，以及所有放在 Git 仓库里的内容。
- **Word/Google Docs** 用于商务提案、面向客户的报告、协作草稿，以及需要复杂视觉排版的文档。

很多工作流程都是先用 Markdown 写作，再转换成其他格式进行分发。

### 把 Markdown 转换为 Word

用 Pandoc 转换非常简单：

```bash
pandoc document.md -o document.docx

# 使用自定义 Word 模板
pandoc document.md -o document.docx --reference-doc=template.docx
```

`--reference-doc` 选项会把公司的 Word 模板（字体、颜色、页眉）应用到转换后的文档上。用 Markdown 写作，以 Word 交付。

### 把 Word 转换为 Markdown

反方向转换也同样可行：

```bash
pandoc document.docx -o document.md

# 同时提取图片
pandoc document.docx -o document.md --extract-media=./images
```

当你需要把现有的 Word 文档迁移到基于 Markdown 的系统时，这会很有用。

### 把 Markdown 转换为 PDF

当 Word 和原始 Markdown 都不适合交付时，PDF 就是通用的答案。printmd 这样的工具能把 Markdown 转换成排版专业的 PDF，字体排版、分页和版式都处理得恰到好处。这让你两全其美：既有用 Markdown 写作的简单，又有排版精良文档的专业外观。

## 实际场景

### 场景 1：软件项目文档

**最佳选择：Markdown。**
文档应该和代码一起放在仓库里。开发者可以在修改代码的同一个拉取请求中更新文档，文档还能自动部署为静态网站。

### 场景 2：季度业务报告

**最佳选择：Word 或 Google Docs。**
需要多位相关人员审阅和批注。文档需要图表、品牌元素和精确的版式。读者期待收到 `.docx` 或 PDF。

### 场景 3：个人博客

**最佳选择：Markdown。**
大多数静态网站生成器和 CMS 平台都使用 Markdown。它快速、可移植，而且不会过时。

### 场景 4：学术论文

**最佳选择：看情况。**
如果论文中数学公式和引用很多，LaTeX（或带 LaTeX 扩展的 Markdown）是理想选择。如果合作者不懂技术，Google Docs 可能更实用。很多研究人员会用 Markdown 配合 Pandoc 写作，再转换成要求的投稿格式。

### 场景 5：会议纪要

**最佳选择：Markdown。**
写得快，分享方便，还能做版本控制。用 Markdown 模板能让整个团队的会议纪要保持一致。

### 场景 6：客户提案

**最佳选择：Word 或 Google Docs。**
客户需要批注和提出修改建议，必须套用品牌模板，最终版本可能还需要签字。

## 如何过渡

如果你目前什么都用 Word，又想把 Markdown 纳入工作流程，可以从小处着手：

1. **个人笔记**：改用 Markdown 记笔记。借助 Obsidian 或 VS Code 等工具，这个过程毫不费力。
2. **会议纪要**：用 Markdown 模板写会议记录。
3. **内部文档**：把团队的 Wiki 或内部文档迁移到 Markdown。
4. **博客文章**：如果你有博客，就用 Markdown 写文章。
5. **项目 README**：从一份结构清晰的 README.md 开始。

不要试图完全取代 Word。让每个工具各司其职。久而久之，你自然会知道在什么场合该用哪种格式。

## 总结

Markdown 和 Word 不是竞争对手，而是满足不同需求、相互补充的工具。Markdown 擅长速度、可移植性、版本控制和技术内容；Word 擅长视觉排版、协作和商务沟通。

问题不在于“哪个更好”，而在于“对这项具体任务来说哪个更好”。一旦不再强求一个工具包揽一切，你的写作流程就会高效得多。

为了 Markdown 的长处去学 Markdown，为了 Word 的长处留着 Word，需要时在两者之间转换。这才是务实的做法。
